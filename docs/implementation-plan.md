# 세부 코드 작성 계획

작성일: 2026년 11월 6일

[승인된 스캐폴드](architecture.md)를 구현하기 위한 세부 계획이다. 이 문서의 단계 번호는 앞으로 코드를 작성할 순서를 뜻한다. 현재는 의존성 설치와 빈 파일 스캐폴드, 개발·빌드 도구 설정을 준비했으며 아래 서비스 기능은 아직 구현하지 않았다.

직접 작성하거나 수정하는 코드·설정·코드 예제는 반드시 **공백 4개**로 들여쓴다. 기존 SvelteKit 프로젝트를 확장하며 웹 서버와 Worker를 같은 저장소에서 관리한다.

## 작업 범위와 현재 상태

rhwp의 웹 편집과 MCP 문서 조작을 연결하고, 이 서비스에 필요한 사용자·문서·브랜치·버전·작업 관리 코드를 작성한다. 웹 서버가 요청을 받고 Worker가 실행하는 구조를 통해 브라우저 종료와 AI 작업의 수명을 분리한다.

요구사항과 단계별 계획을 유지하면서 애플리케이션·Worker·운영 구조용 빈 파일 81개를 만들었다. 명시된 페이지와 API 경로를 마련했으며, 디렉터리만 정한 영역은 빈 `.gitkeep`으로 보존한다. 사용자 요청에 따라 서비스 구현 파일은 0바이트를 유지한다. 기본 경로(`/`)와 추가 페이지는 비어 있고 API 처리·DB 스키마·Worker 실행 로직도 아직 없다.

shadcn-svelte CLI의 `add --all`로 UI 63개 묶음을 설치하고 공식 Lucide Svelte 패키지 `@lucide/svelte`를 추가했다. SvelteKit 3를 유지하면서 Node 어댑터 6, Harness·SDK `0.2.2-rc.1`, rhwp 편집기 `0.8.7`, Drizzle ORM `0.45.4`, `better-sqlite3` `13.0.3`, Zod `4.6.7`을 준비했다. Harness 실행 조건에 맞춰 Node.js 최소 버전은 24.9다. 설치 버전 고정과 실제 연동 검증은 구분한다.

| 구분 | 현재 상태 | 남은 작업 |
| --- | --- | --- |
| 개발·빌드 기반 | 웹 Node 어댑터, Worker 별도 빌드·타입 검사 통과 | 실제 Worker 수명 관리 구현 |
| 코드 스타일 | Prettier 공백 4개 설정과 포맷 명령 준비 | 이후 구현에서도 같은 규칙 유지 |
| 환경·상태 확인 | 환경 변수 예시와 빈 서버 설정·health 파일 준비 | 필수 설정 읽기·검증, 상태 확인 응답 구현 |
| UI·서비스 | UI 라이브러리 설치, 서비스 파일과 경로는 빈 상태 | 인증·문서·버전·AI 기능 구현 |
| DB·테스트 | Drizzle·Vitest·Playwright 설정 준비 | 스키마·마이그레이션·검증 사례 작성 |
| 핵심 연동 | Harness·rhwp 의존성 설치 | OpenRouter·MCP·문서 저장·ARM64 통합 검증 |

이 상태는 **1단계 설정 준비**이며 단계 완료를 뜻하지 않는다. 빈 Worker를 실행하면 할 일 없이 종료하며 개발 watch 모드만 변경을 기다린다. 테스트 디렉터리가 비어 있으므로 테스트 통과를 주장하지 않는다. `data/`와 SQLite 파일은 이후 실행 코드가 생성하며 가짜 DB 파일은 만들지 않았다.

**스캐폴드 검증 결과:** `pnpm lint`, `pnpm check`, `pnpm build`, `pnpm install --frozen-lockfile`, `pnpm peers check`를 확인했다. Linux ARM64·Node.js 24.19에서 SQLite 메모리 DB 쿼리와 Harness SDK·rhwp 편집기 모듈 로딩이 성공했다. 빈 `(app)/+layout.svelte`는 자식 렌더링 누락 경고를 발생시키며 화면 구현 때 연결한다. 라즈베리파이 실기기·OpenRouter·MCP·문서 저장 검증 및 서비스 테스트는 수행 전이다.

`AGENTS.md`와 `.editorconfig`의 공백 4개 규칙, `.gitignore`와 `.gitattributes`의 소스 관리 규칙을 유지한다. `main` 브랜치로 Git 초기화와 저장소 로컬 줄바꿈·공백 검사 설정을 완료했으며, 공개 저장소 [Longcat2957/hwpx-cowork](https://github.com/Longcat2957/hwpx-cowork)를 `origin`으로 연결했다. 웹 서비스의 실제 운영 배포는 10단계의 목표다. 관련 명령은 [설정 문서](git.md)에 정리한다.

모든 화면 단계에서 레이아웃을 작성하기 전에 설치된 shadcn-svelte 컴포넌트와 공식 컴포넌트·블록 목록을 반드시 확인한다. 특히 내비게이션 바·사이드바·대시보드 같은 큰 구성을 먼저 찾아 재사용·조합한다. 기존 제공 여부를 확인하기 전에 유사 UI를 직접 만들지 않으며, 충족되지 않는 부분만 이유를 설명하고 최소한으로 작성한다. 이는 이후 구현의 작업 순서이며 현재 레이아웃 구현이 완료되었다는 뜻은 아니다.

## 1. 실행 기반과 공통 설정

기존 화면과 의존성을 유지하면서 운영 가능한 실행 구조부터 만든다. SvelteKit은 Node 어댑터로 빌드하고, Worker는 별도의 Node 프로세스로 실행한다.

**작성·수정할 파일**

- `package.json`, `vite.config.ts`, `vite.worker.config.ts`, `tsconfig.worker.json`: 웹·Worker 개발 실행, 빌드, 타입 검사 명령.
- `.env.example`, `.gitignore`, `src/lib/server/config/`: 데이터 루트, DB 경로, 서버 비밀 설정, 작업 제한 설정.
- `worker/index.ts`, `worker/dispatcher.ts`: 시작·종료 처리와 작업 대기 루프의 기반.
- `src/routes/api/health/+server.ts`: 서비스 상태 확인.
- `.editorconfig`, `.prettierrc.json`, `.prettierignore`: 탭 없이 공백 4개를 적용하고 확인할 명령. 자동 생성되는 lockfile은 포맷 검사에서 제외한다.
- `vitest.config.ts`, `playwright.config.ts`: 단위·통합 검증과 브라우저 검증의 실행 설정. 빈 테스트 디렉터리와 검증 완료를 구분한다.

**현재 준비한 설정:** `dev:web`·`dev:worker`, `build:web`·`build:worker`, `start:web`·`start:worker`, `check:web`·`check:worker`와 통합 빌드·검사 명령을 마련했다. 웹 출력은 `build/`, Worker 출력은 `dist/worker/`다. `format`·`lint`는 Prettier를 사용하고, `test:unit`·`test:e2e`는 각각 Vitest·Playwright를 사용한다. Drizzle의 `db:generate`·`db:migrate` 명령은 스키마를 구현한 뒤 사용한다. 설치와 설정만으로 아래 완료 기준이 충족되지는 않는다.

현재 Node.js 바이너리가 TypeScript 지원 없이 빌드되어 `.ts` 직접 실행이 불가능하므로 Worker 개발 명령은 `tsx watch`를 사용한다. 운영 실행은 Vite가 만든 JavaScript를 Node로 실행한다.

이미 마련한 문서와 Git 제외 규칙을 유지하면서 실행 설정을 추가한다. 소스 저장소의 브랜치는 `main`을 기준으로 하고, 서비스 내부 문서의 사용자별 브랜치는 3단계의 DB·파일 모델로 구현한다.

OpenRouter 키는 서버에서만 읽는다. 모델 식별자는 환경 변수로 임의 변경하는 설정 대신 고정 정책으로 관리한다. Worker가 공유하는 서버 모듈에는 SvelteKit 전용 요청 객체나 환경 모듈을 넣지 않는다. `#lib` 별칭을 포함한 공통 모듈이 웹 빌드와 Worker 빌드 모두에서 해석되도록 구성한다.

**완료 기준:** 웹과 Worker가 독립적으로 실행·종료되고, 각 빌드와 타입 검사가 통과한다. 운영 필수 설정이 없으면 원인을 표시하며, 클라이언트 번들에 비밀 설정이 들어가지 않는다. 이후 작성한 코드에 공백 4개 규칙을 검사할 수 있다.

## 2. 핵심 연동을 실제 파일로 검증

이 단계는 제품 전체를 만들기 전에 구현 가능성과 제약을 확인하는 단계다. 공식 문서에서 확인한 기능이 이 프로젝트의 라이브러리 버전, 문서 파일, ARM64 환경에서도 연결되는지 검증한다. 현재 문서 작성만으로 전체 연동이 검증된 것은 아니다.

기존에 사용자가 로컬 Codex에서 확인한 rhwp MCP 문서 조작을 바탕으로, 이번 서비스의 Harness·OpenRouter·웹 편집기·라즈베리파이 연결을 검증한다. 특히 문서 수정 성공과 저장 파일의 서식 보존을 함께 확인한다.

**작성할 파일**

- `src/lib/client/rhwp-bridge.ts`, `src/lib/components/editor/`: 브라우저에서만 rhwp를 불러오고 문서 열기·저장·선택 영역 전달을 감싸는 어댑터.
- `worker/runtime/harness.ts`, `model-policy.ts`, `mcp.ts`, `workspace.ts`: Harness SDK, OpenRouter, rhwp MCP와 임시 파일 연결.
- `config/harness/`: 필요한 모델 API와 문서 도구만 활성화하는 Harness 설정.
- `scripts/probes/`, `tests/fixtures/`: 최소 연동 실행과 검증용 HWP·HWPX 문서.

검증 순서는 다음과 같다.

1. HWP와 HWPX를 각각 브라우저에서 열고 문장과 표를 직접 수정한다.
2. 각 형식으로 저장한 파일을 다시 열어 수정 내용과 문서 구조를 확인한다. 형식 변환 결과도 확인하고, 파일 확장자만 바꾸는 방식은 허용하지 않는다.
3. Worker에서 Harness SDK를 실행하고 OpenRouter의 `deepseek/deepseek-v4.1-flash-1017`로 도구 호출을 수행한다.
4. rhwp MCP가 별도 임시 작업본을 수정하게 하고, 저장 결과를 브라우저 편집기로 다시 연다.
5. Harness의 본문 생성·요약 등 모든 LLM 요청이 지정 모델을 사용하며, 다른 모델이나 기본 제공자에 요청하지 않는지 확인한다. 지정 모델을 사용할 수 없으면 명확히 실패 처리한다.
6. MCP에 허용한 파일 범위 밖의 문서를 읽거나 수정할 수 없는지 확인한다. 범용 셸·임의 파일 도구 등 이 서비스에 불필요한 Harness 기능은 노출하지 않는다.
7. 라즈베리파이 5의 ARM64 환경에서 문서 처리 실행 파일, WASM, SQLite 모듈, Harness가 실제로 실행되는지 확인한다.

**완료 기준:** 두 문서 형식의 열기→수정→저장→다시 열기와 지정 모델의 MCP 수정이 성공한다. 본문·표·그림·서식이 포함된 대표 파일로 결과를 확인하고, 가능한 경우 한글 프로그램에서도 저장 파일을 열어 확인한다. 지원하지 않는 편집 기능과 서식 손실은 결과에 기록하며 지원 범위를 과장하지 않는다. 검증한 의존성 버전을 고정한다.

이 단계에서 호환성 문제가 확인되면 어댑터와 실행 방식을 먼저 보완한다. HWP 저장이나 지정 모델 사용 같은 핵심 요구를 임의로 제외하지 않는다. 실제 API 검증에는 서버용 OpenRouter 키가 필요하다.

## 3. DB·파일 저장·버전 기반

**작성할 파일**

- `src/lib/server/db/client.ts`, `schema/`, `repositories/`, `drizzle.config.ts`, `migrations/`.
- `src/lib/server/storage/`: 파일 식별자, 경로 생성, 임시 저장, 확정 저장, 읽기·삭제.
- `src/lib/server/services/documents.ts`, `branches.ts`, `versions.ts`, `sessions.ts`.
- `src/lib/contracts/document.ts`, `version.ts`, `session.ts`, `job.ts`, `events.ts`.

SQLite는 외래 키 검사, WAL, 잠금 대기 시간을 설정한다. 파일 저장과 DB 갱신은 하나의 트랜잭션으로 묶이지 않으므로, 완성된 파일을 원자적으로 확정한 뒤 DB가 참조하게 한다. 중간 실패로 생긴 미참조 파일은 정리할 수 있게 기록한다. 미완성 파일을 성공한 버전으로 노출하지 않는다.

| 데이터 묶음 | 테이블과 주요 제약 |
| --- | --- |
| 구성원·인증 | `users`, `invitations`, `auth_sessions` |
| 문서·브랜치 | `documents`, `branches`; `(document_id, user_id)`는 유일 |
| 저장 버전 | `versions`; 문서, 작성 브랜치, 부모 버전, 복원 기준, 파일 참조 |
| 편집·대화 | `editing_sessions`, `chat_sessions`, `messages`; 기준 버전과 작업본 수정 번호 |
| 참고 자료 | `attachments`; 업로더, 관련 문서·대화, 형식, 파일 참조 |
| 백그라운드 작업 | `jobs`, `job_events`; 실행 소유권, 만료 시각, 이벤트 순서, 결과 파일 |
| 운영 | `app_settings`, `usage_records`; 보관 설정, 작업별 사용량과 제공된 비용 정보 |

토큰과 비용은 API가 반환한 값과 추정값을 구분한다. 가격 정보를 받지 못한 요청의 비용을 확정값처럼 저장하지 않는다.

세션 시작 상태는 복원점으로 보관한다. 세션 중 자동 저장은 작업본의 수정 번호를 갱신한다. 세션 완료·새 세션 시작·명시적 버전 저장 시 최종 상태를 스냅샷으로 확정하며, 변경이 없으면 중복 버전을 만들지 않는다. AI가 문서를 수정하는 각 도구 호출은 사용자용 버전을 만들지 않는다. 브라우저 종료는 세션 완료로 간주하지 않는다.

예를 들어 철수와 영희는 같은 문서의 각자 브랜치를 사용한다. 철수의 다음 대화 세션은 기존 브랜치에 이어지고, 목록에 문서를 새로 추가하지 않는다. 철수가 AI 결과를 작업본에 적용해도 문서 대표 버전과 영희의 작업본은 그대로이며, 대표 버전 지정과 다른 버전 가져오기는 7단계의 명시적 동작으로 제공한다.

**완료 기준:** 두 사용자가 같은 문서를 편집하면 브랜치가 분리되고, 같은 사용자의 중복 요청에는 하나의 브랜치만 생긴다. 보관된 버전은 변경되지 않으며 세션 시작 상태로 복원할 수 있다. DB 갱신과 파일 저장 사이에 실패해도 불완전한 버전을 정상 결과로 표시하지 않는다.

초기 관리자 계정은 서버 명령으로 생성한다. 관리자가 만료되는 일회용 초대 링크를 만들고 구성원에게 전달한다. 비밀번호는 해시로 저장하며, 인증 세션은 서버에서 관리하고 브라우저에는 안전한 세션 쿠키를 사용한다. 초대·로그인에는 시도 제한을 적용한다.

구성원은 문서·버전·문서 대화를 열람하고 자신의 브랜치를 편집한다. 브랜치 소유자와 작업 요청자는 요청 본문의 사용자 ID 대신 인증 세션으로 결정한다. 대표 버전 지정 권한은 구성원에게 제공하고, 구성원 관리와 운영 설정 변경은 관리자에게 제한한다. 비활성화한 사용자의 인증 세션은 폐기한다.

**완료 기준:** 초대 없이 가입할 수 없고, 만료·사용된 초대로 재가입할 수 없다. 로그아웃과 계정 비활성화가 반영된다. 비로그인 API 접근, 다른 사용자의 작업본 수정·작업 취소, 일반 구성원의 관리자 요청을 거부한다. 쿠키 인증을 쓰는 변경 요청은 요청 출처를 검사한다.

**완료 기준:** 문서 업로드→내 브랜치 직접 편집→재접속→다운로드가 연결된다. 저장 결과를 다시 열 수 있으며 HWP와 HWPX가 모두 동작한다. 두 사용자의 편집과 같은 사용자의 오래된 탭 저장이 서로의 결과를 덮어쓰지 않는다.

## 6. AI 작업·대화·결과 반영

**작성할 파일**

- `src/lib/server/jobs/queue.ts`, `leases.ts`, `events.ts`.
- `worker/dispatcher.ts`, `runtime/session-store.ts`, `tasks/edit-document.ts`.
- `worker/results/validate.ts`, `apply.ts`와 2단계의 Harness·MCP 어댑터 연결.
- `src/routes/api/sessions/`, `jobs/`, `events/`, `src/routes/(app)/jobs/`.
- `src/lib/components/chat/`, `jobs/`, `src/lib/client/events.ts`.

요청 시 문서·브랜치·편집 세션·수정 번호·허용된 참고 파일을 기록하고, 실행 기준 파일을 별도로 보관한다. 모델이 임의의 서버 경로나 사용자 ID를 지정해서 작업 대상을 바꾸지 못하게 한다. 대화 연속성에 필요한 Harness 세션 식별자와 실행 기록은 작업·대화 세션에 연결한다.

Worker는 짧은 DB 트랜잭션으로 작업 소유권을 얻고 heartbeat로 유지한다. 만료된 실행의 뒤늦은 응답은 실행 토큰을 검사해 반영하지 않는다. 같은 브랜치의 AI 쓰기 작업은 순서대로 실행하되, 다른 문서의 작업은 서버 전체 동시 실행 한도 안에서 병렬 처리한다. 직접 편집은 AI 실행 중에도 가능하다.

| 상황 | 처리 |
| --- | --- |
| AI 실행 | 기준 파일을 복제한 임시 작업본에서 문서 도구 실행 |
| 정상 완료 | 결과 파일을 검증·확정한 뒤 작업 성공 기록 |
| 작업본이 실행 기준과 동일 | 결과를 내 작업본에 적용하고 수정 번호 증가 |
| 작업본·세션이 달라짐 | 내 작업본과 AI 결과를 모두 보관하고 선택 대기 |
| 브라우저에 미저장 편집이 있음 | 서버 결과로 편집기를 교체하지 않고 미저장본 보존·선택 흐름으로 연결 |
| 결과 선택 중 추가 편집 발생 | 최신 수정 번호로 다시 검사하고 오래된 선택 요청 거부 |
| 브라우저 종료 | 작업은 계속하고 재접속 시 DB의 상태와 이벤트로 복구 |
| 취소 요청 | Harness·도구 중단을 요청하고 취소된 결과의 자동 반영 차단 |
| Worker 비정상 종료 | 중단 상태를 기록하고 기존 결과·실행 기록 확인 후 재개 또는 명시적 재실행 |

AI 작업의 성공 여부와 결과의 반영 여부를 별도로 기록한다. 성공한 작업이라도 충돌한 결과는 선택 대기일 수 있다. 대표 버전은 이 과정에서 자동 변경하지 않는다. 실행 횟수·시간·도구 호출 수를 제한하고, 외부 API 재시도는 이미 실행된 문서 변경을 무조건 반복하지 않게 처리한다.

진행 이벤트는 DB에 순서대로 저장한 뒤 SSE로 전달한다. 연결 복구 시 마지막 이벤트 이후를 읽어 중복 표시를 피한다. 출력 토큰마다 SQLite에 쓰는 대신 이벤트를 적절한 크기로 모으고, 완료·실패·취소 상태는 확정 저장한다. 취소와 결과 반영이 경합할 때 먼저 확정된 상태를 기준으로 응답한다.

**완료 기준:** 대화로 문서를 수정하고 진행 상황을 볼 수 있다. 창을 닫았다가 돌아와도 결과를 확인하며, 동일 사용자가 여러 문서에서 작업할 수 있다. AI 실행 중 직접 편집, 재연결, 취소, Worker 강제 종료를 검증하고 결과 손실·중복 반영·허위 완료가 없어야 한다. 본문과 보조 요청 모두 고정 모델만 사용한다.

## 7. 버전 트리·비교·복원·대표 버전

**작성할 파일**

- `src/lib/components/versioning/`와 문서 상세 화면 연결.
- `src/lib/server/services/versions.ts`, `branches.ts`의 비교·복원·대표 버전 처리.
- `worker/tasks/compare-versions.ts`와 버전 조회·비교·복원·대표 버전 API.

사용자별 브랜치와 세션 버전을 트리로 보여준다. 변경 비교는 우선 문단·표의 추가, 삭제, 내용 변경을 구조적으로 계산하고, 두 버전을 rhwp로 나란히 열어 서식과 배치를 확인할 수 있게 한다. 자동으로 식별할 수 없는 변경은 그렇게 표시한다. 비교 자체는 모델 호출에 의존하지 않는다.

세션 롤백은 과거 파일을 수정하거나 이후 이력을 삭제하는 동작이 아니다. 현재 작업을 복원 가능하게 보관하고 선택한 상태에서 작업을 이어간다. 다른 사람의 버전을 가져와도 내 브랜치 ID를 유지하고 가져온 출처를 기록한다. 브랜치 병합은 구현하지 않는다.

대표 버전 지정은 완성된 버전을 대상으로 수행한다. 이전 대표 버전 식별자를 함께 검사해 다른 사용자가 그사이 바꾼 대표 버전을 조용히 덮어쓰지 않는다. 대표 버전 변경과 개인 브랜치의 기준 변경은 별개다.

**완료 기준:** 두 사용자와 여러 세션의 트리가 실제 파일 관계와 일치한다. 변경 비교, 세션 복원, 다른 브랜치 버전 가져오기, 대표 버전 지정이 가능하며 모든 작업 후 기존 버전을 열 수 있다. 대표 버전 지정 경합도 사용자에게 표시된다.

## 8. AI 새 문서·선택 영역·참고 자료

AI 새 문서는 빈 문서 또는 제공된 양식을 기준으로 임시 작업본을 만들고, 기존 편집 작업과 같은 검증·저장 과정을 거친다. 선택 영역에는 문서 수정 번호와 rhwp에서 얻은 위치 정보를 함께 넣는다. 문서가 바뀌어 위치가 유효하지 않으면 다른 부분을 추측해서 고치지 않고 다시 선택하게 한다.

**완료 기준:** 지시만으로 새 문서를 만들고, 선택한 문장·문단·표를 대상으로 수정할 수 있다. PDF·이미지·HWP/HWPX 참고 자료를 사용하는 흐름을 검증한다. 참고 파일 원본은 변경되지 않으며, 처리 불가능한 첨부는 이유를 표시한다.

## 9. 모바일과 전체 사용 흐름

**작성·수정할 파일**

PC에서는 편집기와 대화를 함께 표시하고, 모바일에서는 대화·문서·버전 보기를 전환한다. 모바일에서 AI 지시, 결과 확인, 버전 선택과 다운로드를 쉽게 이용하도록 구성한다. 직접 편집은 rhwp가 지원하는 범위에서 간단한 수정이 가능하게 연결한다.

저장 중·저장 실패·AI 실행 중·결과 선택 대기 상태를 구분한다. 빈 화면, 긴 작업, API 오류, 재접속에도 사용자가 현재 상태와 다음 동작을 알 수 있게 한다. 한글 입력기 조합 중 자동 저장이나 화면 갱신이 입력을 방해하지 않는지 확인한다.

**완료 기준:** PC와 모바일에서 로그인→문서 열기→AI 지시→결과 확인→대표 버전 반영이 연결된다. 모바일의 간단한 직접 편집, 파일 업로드, 화면 전환, 한글 입력, 연결 복구도 확인한다. 제품 흐름에 내부 Harness 설정이나 서버 경로를 노출하지 않는다.

## 10. 운영·보관·백업·라즈베리파이 배포

**작성할 파일**

- `src/lib/server/services/retention.ts`, `worker/tasks/cleanup.ts`.
- `scripts/backup.ts`, `restore.ts`.
- `deployment/Caddyfile`, `deployment/systemd/deepet-web.service`, `deepet-worker.service`.
- `deployment/rpi_server.md`, `README.md`의 실제 설치·실행·복구 절차.

현재 [라즈베리파이 운영 문서](../deployment/rpi_server.md)는 배포 목표와 완료 기준을 담는다. 실제 접속 정보는 Git에서 제외한 `deployment/rpi_server.local.md`에 보관하며, API 키와 운영 데이터·백업을 소스 커밋에 포함하지 않는다.

30일 보관 설정을 기본값으로 적용한다. 대표 버전, 브랜치 최신 버전, 진행 중 편집·AI 작업의 기준 파일, 미선택 결과와 복원에 필요한 참조는 보호한다. 정리와 새 참조 생성이 경합하지 않게 삭제 전 참조를 다시 검사한다. 첨부와 Harness 기록도 관련 세션의 보관 정책을 따른다. 삭제한 파일에 대해서는 만료 표시와 최소 버전 관계 정보를 남겨 트리를 설명할 수 있게 한다.

초기 백업은 유지보수 상태에서 웹의 변경 요청을 막고 Worker를 안전하게 정지한 뒤 수행한다. SQLite의 일관된 백업과 참조 파일, 필요한 실행 기록, 복원 manifest를 함께 묶는다. DB 파일만 복사하는 방식으로 끝내지 않는다. 서버 비밀 설정의 별도 복구 절차도 문서화한다. 빈 데이터 경로로 복원해 로그인·문서 열기·버전 관계를 확인한다.

systemd로 웹과 Worker를 각각 관리하고 Caddy에서 HTTPS와 외부 접속을 처리한다. SSE 연결과 업로드 제한을 설정한다. 실제 라즈베리파이에서 CPU·메모리·디스크 사용량을 측정해 전체 동시 실행 한도와 파일 크기 제한을 조정한다. 백그라운드 작업량이 늘어도 웹 요청이 지속되는지 확인한다.

**완료 기준:** 지정 도메인에서 로그인과 문서 편집·AI 작업이 동작한다. 서버 재시작 후 작업 상태를 확인할 수 있고, 보호 대상 파일이 정리되지 않는다. 수동 백업을 새 데이터 경로에 복원해 문서와 이력을 읽을 수 있다. 운영 문서에는 검증한 실행 명령과 복구 순서를 남긴다.

## API와 서비스 경계

다음 경로는 구현할 API 묶음이다. 세부 요청 타입은 `contracts/`에 정의하고, HTTP 처리 밖의 규칙은 `server/services/`와 `server/jobs/`에 둔다.

| API 묶음 | 책임 |
| --- | --- |
| `/api/auth` | 로그인·로그아웃·초대 사용 |
| `/api/documents` | 목록·업로드·생성·문서 조회 |
| `/api/documents/:id` 하위 | 내 브랜치·작업본·버전·비교·복원·대표 버전·다운로드 |
| `/api/sessions` | 편집·대화 세션 생성, 메시지 조회, 세션 완료 |
| `/api/attachments` | 참고 자료 업로드·조회 |
| `/api/jobs` | 작업 요청·상태·취소·결과 선택 |
| `/api/events` | 인증된 구성원에게 저장된 진행 이벤트 전달 |
| `/api/health` | 비밀 정보 없이 서비스 상태 확인 |

관리자 구성원·설정 변경은 해당 SvelteKit 서버 액션에서 처리한다. 재전송될 수 있는 작업 요청은 멱등성 키로 중복 생성을 막는다. 대용량 문서 바이트를 SSE 이벤트나 대화 메시지에 포함하지 않는다.

## 전체 완료를 판단하는 검증

테스트 도구는 단위·통합 검증에 Vitest, 브라우저 흐름에 Playwright를 사용한다. 단순 화면 속성을 반복 검증하는 테스트보다 데이터 보존과 실제 편집 흐름을 우선한다. 자동 검증과 실제 한글 프로그램·모바일 기기에서의 수동 확인 결과를 구분해 기록한다.

| 검증 | 통과해야 할 내용 |
| --- | --- |
| 모델 고정 | 본문·요약·보조 작업이 모두 지정 OpenRouter 모델 사용, 장애 시 다른 모델로 전환하지 않음 |
| 문서 형식 | HWP·HWPX 입력과 출력, 직접 편집과 AI 편집 후 다시 열기 |
| 브랜치 | 다른 사용자 분리, 같은 사용자 브랜치 유지, 타인의 작업본 덮어쓰기 방지 |
| 세션 복원 | 직접 편집과 AI 수정 이후 이전 세션 상태로 돌아가도 최신 이력 보존 |
| 충돌 | AI 실행 중 직접 편집·미저장 입력·오래된 탭·대표 버전 경합에서 결과 보존 |
| 작업 지속 | 브라우저 종료·재연결·Worker 종료·취소 후 정확한 상태와 결과 표시 |
| 접근 제어 | 초대·인증·관리자 경계와 작업별 파일 범위 준수 |
| 보관·복구 | 정리 시 참조 보호, 백업을 별도 경로에 복원하고 문서 열기 |
| 실제 환경 | 라즈베리파이 ARM64 실행, PC·모바일 주요 흐름, 공백 4개 코드 스타일 |

다음 코드 작성 작업은 **1단계 실행 기반과 공통 설정의 남은 구현**이다. 설정 읽기·검증, 상태 확인 API, Worker 시작·종료와 대기 루프를 구현하고 완료 기준을 확인한다. 이어서 2단계에서 문서 편집과 AI 연동의 실제 제약을 확인한 뒤 DB·서비스·화면을 차례로 완성한다.
